# Discord manual message setup

This is an operator preparation guide, not evidence of a live installation. Leave the Discord feature off until the isolated connector schema and application composition are ready. Existing manual checks remain available.

## Application preparation

Use one Discord application with **User Install** enabled at the application level. Identity authorization requests only `identify`; the owner completes the existing authenticated Auth0 browser callback at `https://APP/api/scamwin/connectors/expanded/discord/callback`. The callback exchanges the code on the server, verifies the actual `/users/@me` identity, and saves the owner-bound identity. A copied nonce, message author, Discord ID entered in a form, or install URL is not identity proof. The shared authorization service handles one-use state, S256 verifier, secure browser cookie, code claims and local owner/epoch fencing. [Discord OAuth](https://docs.discord.com/developers/topics/oauth2)

Configure the Interactions Endpoint URL as `https://APP/api/scamwin/connectors/discord`. The application public key verifies Ed25519 over the untouched timestamp and request bytes before JSON/PING processing. A successful PING returns `{ "type": 1 }`; invalid signatures return 401. A selected-message request has a 2.7-second application response deadline; it performs no model call, provider API call or file download. Durable event dedupe, encrypted source storage and preparation staging commit before a successful ephemeral response. Real cold-start and database latency still require a provider pilot within Discord's three-second limit. [Interaction verification](https://docs.discord.com/developers/interactions/overview), [response timing](https://docs.discord.com/developers/interactions/receiving-and-responding)

The operator registers the **global** message command using the body in `docs/scamwin-discord-command.example.json` with `POST https://discord.com/api/v10/applications/APPLICATION_ID/commands`. Use a separate operator-held application client-credentials token with `applications.commands.update`; never pass that token to a browser or save it as an owner identity grant. Registration is deliberately not automated by this source change. Do not bulk-overwrite unrelated commands. The command name/type is fixed to the validated application command. [Command creation and operator authentication](https://docs.discord.com/developers/interactions/application-commands)

The template sets `integration_types:[1]` (User Install) and `contexts:[0,1,2]` (server, app DM, private channel). Application-level settings must support User Install. The owner then explicitly allows either messages they select in servers, messages they select in private conversations, or both. These scopes grant permission for each single selected message, not message-history or whole-conversation access. The incoming user-install authorization owner must match the OAuth-linked actor. Server commands additionally need server context and a channel; private contexts must not claim a server. The resolved message must be the one and only selected target and must match that channel. Availability remains subject to Discord's actual command/client/context restrictions. [Installation and interaction contexts](https://docs.discord.com/developers/interactions/application-commands)

The owner selects **Install the message command in Discord** after saving Manual message settings, then uses **Apps → Check with Scamwin** on one message. The install requests `applications.commands` with `integration_type=1`. No bot install, Administrator permission, message-write, server-management or inbox-read scope is requested. A user install does not establish a server-reading bot.

## Server configuration

Use the connector-only application environment, never the publisher project:

- `SCAMWIN_CONNECTORS_ENABLED=true`
- `SCAMWIN_CONNECTOR_DISCORD_ENABLED=true`
- `SCAMWIN_DISCORD_CLIENT_ID` — the configured application ID
- `SCAMWIN_DISCORD_CLIENT_SECRET` — server-only confidential OAuth credential
- `SCAMWIN_DISCORD_PUBLIC_KEY` — exact 32-byte application public key encoded as 64 hexadecimal characters

The accepted plan's canonical `CONNECTORS_ENABLED` and `CONNECTOR_DISCORD_ENABLED` flags map to these existing application-prefixed environment names. No Discord automatic flag exists. Any global automatic flag still leaves the Discord adapter Manual only, with no pull/history/Gateway capability.

The root composition supplies the guarded isolated connector database/keyring and common authorization persistence to `createDiscordIntegration`; registers its adapter and `registerDiscordServices` factory; includes `scamwin-discord-schema.ts` in connector-only schema configuration; and mounts `DiscordConnectionSetup` inside the existing Account connection UI. All new tables are connector-only. This task does not apply DDL, alter the main database, create a Discord application, register commands or deploy anything.

## Boundaries and pilot acceptance

OAuth profile access-token expiry does not erase a verified identity link: a fresh signed command supplies current actor and selected-message authority. The local connection must remain active, in Manual, with the current owner/epoch, retained verified identity and explicit context scope; the hashed link expires 90 days after setup. Disconnect, erasure, changed scope/epoch and relinking fence stale data. Actual profile reads and refresh still use the common server-side authorization service. On disconnect, common cleanup captures the grant before the local fence, then calls the fixed form-encoded Discord revoke endpoint after local erasure. Remove the installed app in Discord as needed. Provider-side removal/revocation and retained-link behavior must be checked in the live pilot.

Bodies/context expire within 30 days of the trusted app receipt when the user explicitly selects a message; encrypted provider references and media URLs expire within seven days of that receipt; dedupe and bounded link/activity metadata within 90 days. Older messages may be explicitly selected. Their original creation/edit timestamps are preserved only in the encrypted Discord reference, do not extend retention, and are not prepended to the message text. A volatile signed CDN URL may expire sooner than the application retention window; that file remains an explicit coverage gap. Only selected PNG/JPEG/WebP attachments on the exact saved `cdn.discordapp.com/attachments/CHANNEL/ATTACHMENT/NAME` path may load. Signed query expiry, origin, path, redirects, streaming bytes and deadline are checked again in the worker. No bearer credential is sent to the CDN. Source deletion, connection changes, seven-day expiry and revoked local ownership reject old media references. Signed CDN URLs stay in encrypted seven-day references and never enter model input or DTOs. Expired/unsupported files, embeds, stickers, reply context and parser overflow remain explicit incomplete coverage.

Run the offline check with `node scripts/check-scamwin-discord.mjs`; `--print-command` prints only the static command template. Focused synthetic coverage uses `node --import tsx --test tests/scamwin-discord.test.ts` with a fresh local PGlite database and generated signing keys. It cannot establish a real OAuth/Discord installation.

Before enabling a real pilot, verify provider OAuth/linkage/denial, user installation, command registration and available contexts, signed PING and invalid-signature probes, one selected-message receipt, 3-second cold/warm response times, duplicate retry recovery, local pause/disconnect/relink, app removal and grant revocation, expired image URLs, unsupported content, isolated retention cleanup, existing quota admission and owner-visible private status. Automatic Discord monitoring remains unavailable: no persistent free Gateway runtime, heartbeat/resume/recovery, channel authorization or message-content eligibility has been qualified.
