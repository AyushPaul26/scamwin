# Scamwin integration review

Reviewed the root-owned policy, assessment, AI, collector, origin probe, investigation pipeline, official references, dispatch, server/readiness modules, server actions, Scamwin API routes and Trigger tasks. This was an ordinary implementation review, with targeted local reproductions and domain tests. No external services or real database were contacted.

Concrete findings were reported as they were found and addressed during integration:

1. **Receiving-money risk was unreachable from ordinary intake text.** `assessEvidence` requires the explicit `receive_money` value, while intake previously collected free text. A local reproduction with the same observed outgoing payment returned `high_risk` for `receive_money`, and `inconclusive` for both “Receive money” and the form’s example “Scan a QR to receive money.” Intake now uses explicit action choices and renders readable labels, preserving the deterministic user-selected rule.
2. **Cancellation was acknowledged before the active worker stopped.** The action immediately changed `cancel_requested` to `canceled`, releasing the owner’s active-run slot before provider cleanup. The action now requests cancellation only. Store cancellation atomically finalizes an unclaimed queued check, while claimed states remain `cancel_requested` until the worker finishes. A new regression test verifies an unclaimed canceled check cannot subsequently be claimed.
3. **Polling returned image bytes repeatedly.** Artifact metadata was stripped, but the hydrated check input still contained screenshot data URLs. The check API and list action now strip those bytes; authenticated artifact delivery remains separate.
4. **DNS resolution escaped the probe deadline.** The twelve-second signal previously applied after awaiting DNS. The probe now races resolution against cancellation/deadline before opening a pinned TLS connection.
5. **An HTTP URL was mislabeled as failed certificate validation.** The probe previously emitted observed `tls.valid=false` without performing a handshake. HTTP now produces an explicit `not_checked` TLS observation and a separate lexical unencrypted-HTTP URL concern.
6. **Follow-up retries retained a consumed request key after a definite AI failure.** The server reserves the key before the model request. The UI now releases the key on a definitive `ai_unavailable` result and when the question changes, while retaining it for uncertain transport failures.
7. **Queued/claimed checks depended on daily cleanup to time out.** Owner reads, internal reads, history and new admission now lazily fail overdue active runs at 300 seconds, increment revision/generation, revoke dispatch and permit a new owner check. New tests exercise reads and admission without a prior maintenance run.
8. **Unsigned local retraction left obsolete dispatch/publication work.** Retraction now revokes obsolete unsigned operations/outbox entries. A warning that never reached chain signing becomes `local_only` instead of sending a retract transaction for a nonexistent assertion. Pending publication selection filters stale revisions/expired unsigned consent and prioritizes signed transactions needing reconciliation.
9. **Consent omitted version/TTL, and submission-key reuse ignored changed inputs.** Consent hashes now bind schema version 1 and a 604800-second public assertion TTL. An immutable canonical submission hash includes validated text and original image names/type/bytes before artifact separation; changed input under the same key returns `submission_conflict`, while identical retries remain idempotent after image expiry.
10. **PostgreSQL could not infer two polymorphic JSON parameter types.** Independent local PostgreSQL-engine review identified unknown types inside `jsonb_build_object`; publication lease tokens and reserved-fee strings now carry explicit `::text` casts. The Web3 agent is exercising the broader SQL adapter against an isolated local engine.

The root intentionally makes failed Trigger dispatch terminal for that check, with visible unavailability and a new-check path, rather than silently retrying uncertain execution. Its outbox entry is not eligible once the check is terminal. This differs from automatic recoverable dispatch in the earlier design; it preserves the chosen free-tier bounded behavior and avoids an indefinite normal-looking queue.

The reviewed implementation keeps target collection out of Vercel, restricts live destinations to configured operator-owned origins, disables arbitrary-host collection, uses fresh remote browser contexts, blocks sensitive submissions, constrains task/browser/model time and output, validates model JSON and evidence references, preserves owner isolation and private artifact expiry, and does not select a paid fallback. Provider account/terms capability and real deployment availability remain setup checks; configuration presence is not represented as a successful live test.

Final correlation coverage now uses indexed, owner-scoped hostname/recipient/endpoint HMAC fingerprints rather than only the latest twenty same-host cases. Indicator rows store no raw values, reject infrastructure-only issuer/CDN kinds, enforce a twenty-indicator cap with serialized immutable inserts, and exclude deleted, expired and foreign-owner cases. Regression tests demonstrate repeated recipient matches across unrelated hostnames without exposing a second owner’s history. The parent derives the HMAC from an optional server secret and records explicit unavailability when it is absent.

The final combined input, store, investigation, publication and correlation tests passed: **40 tests, 0 failures**, including **29 input/store tests**. The first combined correlation run exposed the parent’s old synthetic pipeline expectation (`completed` versus the new honest `partial` when the HMAC secret was absent); the parent updated that fixture to supply an explicit test secret. Final application typecheck/build/browser verification is owned by the parent task. The earlier complete repository suite had 120 passes, 19 failures and one cancellation in the pre-existing generic bot/chat/sandbox tests; their names are recorded in `scamwin-data-report.md`. No broad-suite passing claim is made here.
